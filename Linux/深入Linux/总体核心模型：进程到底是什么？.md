

你这五章其实是在讲 Linux/UNIX 进程生命周期的一整套机制：

```text
创建进程：fork()
        ↓
子进程运行
        ↓
子进程可能执行新程序：exec()
        ↓
子进程终止：exit() / _exit()
        ↓
父进程回收子进程：wait() / waitpid()
```

可以把它理解成一句话：

**fork() 负责“生孩子”，exec() 负责“换程序”，exit() 负责“结束自己”，wait() 负责“父进程收尾”。**

------

# 总体核心模型：进程到底是什么？

在操作系统里，一个进程不是单纯的“程序文件”。

程序文件，比如：

```bash
/bin/ls
./a.out
```

只是硬盘上的文件。

而进程是：

```text
正在运行中的程序 + 它的内存 + 它打开的文件 + 它的寄存器状态 + 它的进程 ID 等信息
```

例如你运行：

```bash
./my_program
```

操作系统会创建一个进程，这个进程拥有：

```text
PID：进程编号
内存空间：代码段、数据段、堆、栈
文件描述符表：stdin、stdout、stderr、打开的文件
环境变量
信号处理方式
当前工作目录
用户 ID、组 ID
```

这五章就是围绕这些东西在讲：

```text
第24章：进程怎么创建？
第25章：进程怎么死？
第26章：父进程怎么知道子进程死了？
第27章：一个进程怎么执行另一个程序？
第28章：fork 和 exec 更深入的细节
```

------

# 第24章：进程的创建

## 24.1 fork()、exit()、wait()、execve() 的整体关系

这几个函数经常一起出现。

典型模式是：

```c
pid_t pid = fork();

if (pid == 0) {
    // 子进程
    execve(...);
    _exit(1);
} else {
    // 父进程
    wait(NULL);
}
```

可以这样理解：

| 函数                   | 作用                           | 类比           |
| ---------------------- | ------------------------------ | -------------- |
| `fork()`               | 创建一个几乎一模一样的新进程   | 复制一个自己   |
| `execve()`             | 用新程序替换当前进程的程序内容 | 换脑子         |
| `exit()` / `_exit()`   | 结束当前进程                   | 自己退出       |
| `wait()` / `waitpid()` | 父进程等待子进程结束           | 给子进程“收尸” |

重点是：

**fork() 之后有两个进程，exec() 之后还是一个进程，只是程序变了。**

------

## 24.2 创建新进程：fork()

`fork()` 是创建新进程的核心系统调用。

基本形式：

```c
pid_t pid = fork();
```

它有一个很特别的地方：

**一次调用，返回两次。**

因为 `fork()` 会创建子进程，所以从 `fork()` 返回之后，父进程和子进程都会继续执行后面的代码。

返回值不同：

```c
pid_t pid = fork();

if (pid == -1) {
    // 创建失败
} else if (pid == 0) {
    // 子进程
} else {
    // 父进程，pid 是子进程的 PID
}
```

### 为什么子进程里 `pid == 0`？

因为子进程需要知道：

```text
我就是新创建出来的那个进程。
```

父进程需要知道：

```text
我创建的子进程是谁？
```

所以父进程拿到子进程 PID，子进程拿到 0。

------

## fork() 之后父子进程的关系

假设代码是：

```c
printf("Before fork\n");

pid_t pid = fork();

printf("After fork\n");
```

输出可能是：

```text
Before fork
After fork
After fork
```

原因：

```text
fork() 之前只有一个进程，所以 Before fork 打印一次。
fork() 之后有父子两个进程，所以 After fork 打印两次。
```

重点理解：

```text
fork() 不是“跳到子进程去执行”。
fork() 是从当前位置复制出一个新进程。
父进程和子进程从 fork() 后面继续执行。
```

------

## 24.2.1 父、子进程间的文件共享

这是一个很重要的点。

`fork()` 后，子进程会继承父进程打开的文件描述符。

例如父进程已经打开了一个文件：

```c
int fd = open("test.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);

fork();

write(fd, "hello\n", 6);
```

父子进程都会拥有 `fd`。

但是这里要注意：

**父子进程的文件描述符表是各自一份，但它们指向同一个打开文件描述对象。**

可以画成这样：

```text
父进程 fd 表              子进程 fd 表
fd 3 ─────┐              fd 3 ─────┐
          ↓                        ↓
       同一个打开文件对象
       包含：文件偏移量、打开状态标志
```

这意味着：

### 1. 文件偏移量共享

如果父进程写了 5 个字节，文件偏移量向后移动 5。

子进程再写时，会从新的偏移量继续写，而不是从头写。

例如：

```c
write(fd, "AAA", 3);
fork();
write(fd, "BBB", 3);
```

可能结果不是简单固定的，因为父子谁先写不确定。

可能是：

```text
AAABBBBBB
```

因为父子都写了 `"BBB"`。

### 2. 打开文件状态标志共享

例如 `O_APPEND` 这类状态，父子进程共享。

### 3. 文件描述符本身不完全共享

如果子进程关闭自己的 `fd`：

```c
close(fd);
```

不会直接关闭父进程的 `fd`。

因为父进程和子进程各有自己的文件描述符表。

可以理解成：

```text
钥匙各有一把，但指向的是同一个房间。
一个人丢了钥匙，不影响另一个人的钥匙。
```

------

## 24.2.2 fork() 的内存语义

`fork()` 后，父子进程的内存看起来一样。

例如：

```c
int x = 10;

pid_t pid = fork();

if (pid == 0) {
    x = 20;
    printf("child x=%d\n", x);
} else {
    x = 30;
    printf("parent x=%d\n", x);
}
```

输出可能是：

```text
child x=20
parent x=30
```

重点：

**父子进程的内存是相互独立的。**

子进程修改变量 `x`，不会影响父进程。

父进程修改变量 `x`，也不会影响子进程。

------

## 那 fork() 是不是把内存完整复制一份？

从逻辑上看，是的。

但从性能上看，现代操作系统不会傻傻地立刻复制所有内存。

它使用一种技术：

```text
写时复制，Copy-On-Write，COW
```

意思是：

```text
刚 fork() 时，父子进程暂时共享同一份物理内存。
只要双方都只是读，就不复制。
一旦某个进程要写某一页内存，操作系统才复制那一页。
```

这样效率很高。

例如一个进程占用 2GB 内存，如果 fork() 马上复制 2GB，会非常慢。

但有了 COW，fork() 可以很快。

------

## 24.3 vfork()

`vfork()` 是一个比较危险、现在不太推荐普通使用的系统调用。

它的目的：

```text
创建子进程后，子进程马上 exec()
```

早期系统里，`fork()` 复制内存成本很高，所以有了 `vfork()`。

`vfork()` 的特点：

```text
子进程和父进程临时共享地址空间。
在子进程 exec() 或 _exit() 之前，父进程会被阻塞。
```

这很危险。

例如：

```c
int x = 10;

pid_t pid = vfork();

if (pid == 0) {
    x = 20;
    _exit(0);
}

printf("%d\n", x);
```

父进程里的 `x` 可能被子进程改掉。

所以要记住：

```text
普通创建进程用 fork()。
fork 后马上 exec 时，某些系统内部可能优化。
除非非常清楚后果，否则不要随便用 vfork()。
```

------

## 24.4 fork() 之后的竞争条件

`fork()` 后，父进程和子进程谁先运行？

答案是：

```text
不确定。
```

操作系统调度器决定。

例如：

```c
pid_t pid = fork();

if (pid == 0) {
    printf("child\n");
} else {
    printf("parent\n");
}
```

输出可能是：

```text
child
parent
```

也可能是：

```text
parent
child
```

这就是竞争条件的一种表现。

**竞争条件就是程序结果依赖于多个进程或线程的执行时序。**

如果你的程序正确性依赖于“父进程一定先执行”或者“子进程一定先执行”，那就是危险的。

------

## 24.5 同步信号以规避竞争条件

如果确实需要控制顺序，就要同步。

比如希望：

```text
子进程先做完某件事，父进程再继续
```

可以用信号、管道、信号量等同步机制。

信号同步的思想是：

```text
子进程完成后给父进程发一个信号。
父进程在收到信号之前暂停等待。
```

类似现实生活：

```text
孩子做完作业后喊一声“我做完了”。
父母听到后再检查。
```

但是信号编程容易有细节问题，比如：

```text
信号可能在父进程准备等待之前就已经发出。
```

所以实际写代码时要配合信号屏蔽字，避免信号丢失导致死等。

------

## 第24章重点总结

这一章最核心的几个点：

```text
1. fork() 创建子进程。
2. fork() 一次调用，两次返回。
3. 父进程中 fork() 返回子进程 PID。
4. 子进程中 fork() 返回 0。
5. 父子进程内存逻辑上独立。
6. 父子进程共享打开文件描述对象，所以共享文件偏移量。
7. fork() 后父子谁先运行不确定。
8. vfork() 危险，子进程应尽快 exec() 或 _exit()。
```

# 第25章：进程的终止

第25章讲的是：

```text
进程如何结束？
结束时系统会做什么？
exit() 和 _exit() 有什么区别？
```

------

## 25.1 进程的终止：_exit() 和 exit()

进程终止有几种方式：

```text
1. main() 函数 return
2. 调用 exit()
3. 调用 _exit()
4. 被信号杀死
```

例如：

```c
int main() {
    return 0;
}
```

等价于：

```c
int main() {
    exit(0);
}
```

注意：这是 C 运行时帮你做的。

------

## exit() 和 _exit() 的区别

这是重点。

| 函数      | 层次     | 会不会刷新 stdio 缓冲区 | 会不会调用退出处理程序 |
| --------- | -------- | ----------------------- | ---------------------- |
| `exit()`  | C 库函数 | 会                      | 会                     |
| `_exit()` | 系统调用 | 不会                    | 不会                   |

### exit()

`exit()` 比较“优雅”。

它会做这些事情：

```text
1. 调用通过 atexit() 注册的退出处理函数
2. 刷新 stdio 缓冲区
3. 关闭标准 I/O 流
4. 最后调用 _exit() 结束进程
```

### _exit()

`_exit()` 比较“直接”。

它会直接告诉内核：

```text
这个进程结束了。
```

不会刷新 C 标准库缓冲区，也不会调用 `atexit()` 注册的函数。

------

## 举个例子理解缓冲区

代码：

```c
printf("hello");
_exit(0);
```

可能没有输出。

因为 `"hello"` 没有换行，可能还在 stdio 缓冲区里。

如果写：

```c
printf("hello");
exit(0);
```

通常会输出：

```text
hello
```

因为 `exit()` 会刷新缓冲区。

------

## 25.2 进程终止的细节

当一个进程终止时，内核会做很多清理工作：

```text
1. 关闭所有打开的文件描述符
2. 释放内存
3. 释放文件锁等资源
4. 给父进程发送 SIGCHLD 信号
5. 保存终止状态，等待父进程 wait()
```

这里有一个关键点：

**进程死了，不代表它的信息马上完全消失。**

如果父进程还没有调用 `wait()` 读取它的终止状态，它会变成：

```text
僵尸进程 zombie
```

------

## 25.3 退出处理程序

可以用 `atexit()` 注册退出处理程序。

例如：

```c
void cleanup(void) {
    printf("cleaning up\n");
}

int main() {
    atexit(cleanup);
    exit(0);
}
```

输出：

```text
cleaning up
```

退出处理程序适合做：

```text
释放临时资源
删除临时文件
写日志
关闭应用层资源
```

但是注意：

```text
调用 _exit() 不会执行 atexit() 注册的函数。
```

------

## 25.4 fork()、stdio 缓冲区以及 _exit() 之间的交互

这是非常经典、也非常容易考的点。

看这个程序：

```c
printf("Hello");

fork();

exit(0);
```

可能输出：

```text
HelloHello
```

为什么？

因为 `printf("Hello")` 没有换行，内容可能还在用户态 stdio 缓冲区里。

`fork()` 时，子进程复制了父进程的内存。

stdio 缓冲区也被复制了。

所以：

```text
父进程缓冲区里有 "Hello"
子进程缓冲区里也有 "Hello"
```

然后父子进程都调用 `exit()`。

`exit()` 会刷新缓冲区。

于是输出两次。

------

## 如果换成 _exit()

```c
printf("Hello");

fork();

_exit(0);
```

可能什么也不输出。

因为 `_exit()` 不刷新 stdio 缓冲区。

------

## 如何避免重复输出？

方法一：fork 前刷新缓冲区。

```c
printf("Hello");
fflush(stdout);

fork();

exit(0);
```

方法二：在子进程出错退出时用 `_exit()`。

典型写法：

```c
pid_t pid = fork();

if (pid == 0) {
    execlp("ls", "ls", NULL);
    _exit(127);   // exec 失败才会执行这里
}
```

为什么这里用 `_exit()`？

因为子进程是从父进程复制出来的，可能继承了父进程的 stdio 缓冲区。

如果 exec 失败后调用 `exit()`，可能把父进程缓冲区重复刷新一遍。

------

## 第25章重点总结

```text
1. exit() 是库函数，_exit() 是系统调用。
2. exit() 会刷新 stdio 缓冲区，会执行退出处理程序。
3. _exit() 直接终止进程，不刷新 stdio，不执行 atexit()。
4. fork() 会复制 stdio 缓冲区。
5. fork() 之后子进程中执行 exec 失败，通常用 _exit() 退出。
6. 进程终止后，会给父进程留下终止状态，等待父进程 wait()。
```

------

# 第26章：监控子进程

这一章讲的是父进程如何知道子进程结束，以及如何回收子进程。

核心函数：

```text
wait()
waitpid()
waitid()
wait3()
wait4()
```

其中最重要的是：

```text
wait()
waitpid()
```

------

## 26.1 等待子进程

当子进程结束后，它的退出状态会保存在内核中。

父进程需要调用 `wait()` 或 `waitpid()` 来读取这个状态。

这个动作通常叫：

```text
回收子进程
```

如果父进程不回收，子进程会成为僵尸进程。

------

## 26.1.1 wait()

基本形式：

```c
pid_t wait(int *status);
```

作用：

```text
等待任意一个子进程终止。
```

例如：

```c
int status;
pid_t child_pid = wait(&status);
```

如果没有子进程已经结束，`wait()` 会阻塞。

如果有子进程已经结束，`wait()` 立即返回。

返回值是：

```text
被回收的子进程 PID
```

------

## wait() 的问题

如果父进程有多个子进程：

```text
child1
child2
child3
```

调用：

```c
wait(&status);
```

你不知道它等到的是哪一个。

它会回收任意一个已经终止的子进程。

如果你想等指定子进程，就用 `waitpid()`。

------

## 26.1.2 waitpid()

基本形式：

```c
pid_t waitpid(pid_t pid, int *status, int options);
```

`pid` 参数很重要。

| pid 值      | 含义                             |
| ----------- | -------------------------------- |
| `pid > 0`   | 等待指定 PID 的子进程            |
| `pid == -1` | 等待任意子进程，类似 wait()      |
| `pid == 0`  | 等待与调用者同进程组的任意子进程 |
| `pid < -1`  | 等待指定进程组中的任意子进程     |

最常用：

```c
waitpid(child_pid, &status, 0);
```

表示：

```text
等待指定的 child_pid 结束。
```

------

## waitpid() 的 options

常见选项：

| 选项         | 含义                               |
| ------------ | ---------------------------------- |
| `0`          | 阻塞等待                           |
| `WNOHANG`    | 不阻塞，没有子进程结束就立即返回 0 |
| `WUNTRACED`  | 也报告被停止的子进程               |
| `WCONTINUED` | 也报告被继续运行的子进程           |

例如：

```c
pid_t result = waitpid(-1, &status, WNOHANG);

if (result == 0) {
    printf("no child exited yet\n");
}
```

这适合父进程不能卡住等待的情况。

------

## 26.1.3 等待状态值

`wait()` 和 `waitpid()` 会把子进程状态放到 `status` 里。

但不能直接把它当成退出码。

要用宏解析。

常见宏：

| 宏                     | 含义                      |
| ---------------------- | ------------------------- |
| `WIFEXITED(status)`    | 子进程是否正常 exit 结束  |
| `WEXITSTATUS(status)`  | 获取正常退出的退出码      |
| `WIFSIGNALED(status)`  | 子进程是否被信号杀死      |
| `WTERMSIG(status)`     | 获取杀死子进程的信号      |
| `WIFSTOPPED(status)`   | 子进程是否被信号停止      |
| `WSTOPSIG(status)`     | 获取停止信号              |
| `WIFCONTINUED(status)` | 子进程是否被 SIGCONT 恢复 |

例子：

```c
int status;
pid_t pid = wait(&status);

if (WIFEXITED(status)) {
    printf("child exited, status=%d\n", WEXITSTATUS(status));
} else if (WIFSIGNALED(status)) {
    printf("child killed by signal %d\n", WTERMSIG(status));
}
```

------

## 正常退出和异常终止

例如子进程：

```c
exit(7);
```

父进程可以通过：

```c
WEXITSTATUS(status)
```

得到 `7`。

如果子进程被：

```bash
kill -9 pid
```

杀死，那么：

```c
WIFSIGNALED(status)
```

为真，`WTERMSIG(status)` 得到 `9`。

------

## 26.1.4 从信号处理程序中终止进程

有些程序在收到信号后需要清理再退出。

例如：

```c
void handler(int sig) {
    // 不建议在这里做复杂事情
    _exit(128 + sig);
}
```

但是信号处理程序里能安全调用的函数很少。

不要随便在信号处理程序中调用 `printf()`、`malloc()` 这类函数。

更稳妥的方式是：

```text
信号处理程序只设置一个标志变量。
主循环检查这个标志，然后正常退出。
```

------

## 26.1.5 waitid()

`waitid()` 比 `waitpid()` 更灵活，可以获得更详细的信息。

大致形式：

```c
waitid(idtype, id, siginfo_t *infop, options);
```

它可以把子进程信息放进 `siginfo_t` 结构。

不过普通学习重点还是：

```text
掌握 wait() 和 waitpid()。
知道 waitid() 更现代、更细致。
```

------

## 26.1.6 wait3() 和 wait4()

`wait3()` 和 `wait4()` 可以额外获得资源使用信息。

例如子进程用了多少 CPU 时间。

它们比 `wait()` / `waitpid()` 更偏高级和系统监控场景。

普通重点：

```text
wait4() ≈ waitpid() + 资源使用统计
```

------

# 26.2 孤儿进程与僵尸进程

这是这一章的核心概念。

------

## 僵尸进程 zombie

子进程已经结束，但父进程没有调用 `wait()` 回收。

此时子进程变成僵尸进程。

```text
子进程：我已经死了。
内核：你的退出状态还没人领取，先保留着。
父进程：还没 wait。
```

于是系统里留下一个僵尸进程表项。

僵尸进程不占用普通内存和 CPU，但占用进程表项。

如果太多，会影响系统创建新进程。

### 怎么看到僵尸进程？

用：

```bash
ps aux
```

状态可能显示：

```text
Z
```

或者：

```text
<defunct>
```

------

## 为什么需要僵尸进程？

因为父进程需要知道：

```text
子进程是正常退出的吗？
退出码是多少？
是不是被信号杀死的？
```

所以内核必须暂时保存这些信息。

------

## 怎么避免僵尸进程？

父进程调用：

```c
wait();
waitpid();
```

如果有很多子进程，经常写成循环：

```c
while (waitpid(-1, NULL, WNOHANG) > 0) {
    // 回收所有已经结束的子进程
}
```

------

## 孤儿进程 orphan

孤儿进程是：

```text
父进程先死了，子进程还活着。
```

例如：

```text
父进程结束
子进程仍然运行
```

这时子进程会被系统中的特殊进程接管。

传统上是 `init` 进程，现代 Linux 上常常是 `systemd` 或子收割进程。

孤儿进程本身不是错误。

它只是：

```text
没有原来的父亲了，被系统接管。
```

------

## 僵尸进程 vs 孤儿进程

| 类型     | 状态                        | 问题           |
| -------- | --------------------------- | -------------- |
| 僵尸进程 | 子进程已经死，父进程没 wait | 需要父进程回收 |
| 孤儿进程 | 父进程死了，子进程还活着    | 会被系统接管   |

一句话区分：

```text
僵尸：孩子死了，父亲没收尸。
孤儿：父亲死了，孩子还活着。
```

------

# 26.3 SIGCHLD 信号

当子进程状态变化时，内核会给父进程发送 `SIGCHLD` 信号。

常见状态变化：

```text
子进程终止
子进程停止
子进程继续运行
```

最重要的是：

```text
子进程终止时，父进程收到 SIGCHLD。
```

------

## 26.3.1 为 SIGCHLD 建立信号处理程序

父进程可以给 `SIGCHLD` 设置处理程序。

核心思想：

```c
void sigchld_handler(int sig) {
    while (waitpid(-1, NULL, WNOHANG) > 0) {
        // 回收所有已经结束的子进程
    }
}
```

为什么要用 `while`？

因为多个子进程可能几乎同时结束，但标准信号可能不会排队保存多个同类信号。

也就是说：

```text
死了 5 个子进程，父进程可能只收到一次 SIGCHLD。
```

所以收到一次 `SIGCHLD` 后，应该循环回收所有已经结束的子进程。

为什么要用 `WNOHANG`？

因为信号处理程序不能阻塞。

如果没有已终止子进程，`waitpid()` 应该马上返回。

------

## 26.3.2 向已停止的子进程发送 SIGCHLD

`SIGCHLD` 不只在子进程终止时发送。

子进程被停止时，父进程也可能收到。

例如子进程收到：

```text
SIGSTOP
SIGTSTP
```

父进程可以通过 `waitpid()` 配合 `WUNTRACED` 检测。

------

## 26.3.3 忽略终止的子进程

如果父进程不关心子进程退出状态，可以设置：

```c
signal(SIGCHLD, SIG_IGN);
```

在某些系统上，这会让系统自动回收终止的子进程，避免僵尸进程。

也可以设置 `SA_NOCLDWAIT`。

但学习时要注意：

```text
这种行为在不同 UNIX 系统历史上有差异。
需要写可移植程序时要小心。
```

------

## 第26章重点总结

```text
1. 子进程结束后，父进程要 wait() 或 waitpid()。
2. 不 wait 会产生僵尸进程。
3. wait() 等任意子进程。
4. waitpid() 可以等指定子进程，也可以非阻塞等待。
5. status 需要用 WIFEXITED、WEXITSTATUS 等宏解析。
6. SIGCHLD 是子进程状态变化时发给父进程的信号。
7. SIGCHLD 处理程序里常用 waitpid(-1, NULL, WNOHANG) 循环回收。
8. 僵尸进程是“死了没被回收”，孤儿进程是“父进程死了但自己还活着”。
```

------

# 第27章：程序的执行

第27章讲的是 `exec` 家族。

这一章非常关键，因为它和 `fork()` 经常组合使用。

------

## 27.1 执行新程序：execve()

`execve()` 是核心系统调用。

形式：

```c
int execve(const char *pathname, char *const argv[], char *const envp[]);
```

它的作用：

```text
把当前进程的程序映像替换成一个新程序。
```

注意重点：

```text
execve() 不创建新进程。
execve() 不改变 PID。
execve() 成功后不会返回。
```

为什么不会返回？

因为当前进程的代码、数据、堆、栈都被新程序替换了。

原来的程序已经不存在了。

只有失败时才返回 `-1`。

------

## execve() 的三个参数

### 1. pathname

要执行的程序路径：

```c
"/bin/ls"
```

### 2. argv

传给新程序的参数数组。

例如命令：

```bash
ls -l /tmp
```

对应：

```c
char *argv[] = {"ls", "-l", "/tmp", NULL};
```

注意：

```text
argv[0] 通常是程序名。
数组必须以 NULL 结尾。
```

### 3. envp

环境变量数组。

例如：

```c
char *envp[] = {"PATH=/bin:/usr/bin", "HOME=/home/user", NULL};
```

也必须以 `NULL` 结尾。

------

## execve() 示例

```c
char *argv[] = {"ls", "-l", "/tmp", NULL};
char *envp[] = {"PATH=/bin:/usr/bin", NULL};

execve("/bin/ls", argv, envp);

// 如果 execve 成功，不会执行到这里
perror("execve");
_exit(127);
```

------

## fork() + exec() 的经典组合

Shell 执行命令时，大致就是这样：

```c
pid_t pid = fork();

if (pid == 0) {
    // 子进程执行新程序
    execlp("ls", "ls", "-l", NULL);
    _exit(127); // exec 失败
} else {
    // 父进程等待子进程
    waitpid(pid, NULL, 0);
}
```

为什么要这样设计？

因为：

```text
fork() 创建子进程。
子进程 exec() 变成新程序。
父进程继续保留 shell 自己。
```

如果 shell 直接 exec `ls`，那 shell 自己就没了。

所以 shell 必须：

```text
先 fork，再让子进程 exec。
```

------

## 27.2 exec() 库函数

`execve()` 是系统调用，其他 `exec` 函数大多是库函数封装。

常见有：

```c
execl()
execle()
execlp()
execv()
execvp()
execvpe()
```

它们名字里的字母有含义。

------

## exec 函数命名规律

| 字母 | 含义                             |
| ---- | -------------------------------- |
| `l`  | list，参数一个一个列出来         |
| `v`  | vector，参数用数组传             |
| `p`  | PATH，使用 PATH 环境变量搜索程序 |
| `e`  | environment，显式传入环境变量    |

------

## 27.2.1 环境变量 PATH

如果用：

```c
execl("/bin/ls", "ls", "-l", NULL);
```

必须写完整路径。

如果用：

```c
execlp("ls", "ls", "-l", NULL);
```

它会根据 `PATH` 搜索 `ls`。

就像 shell 中输入：

```bash
ls
```

不需要写 `/bin/ls`。

因为 shell 会查 `PATH`：

```bash
echo $PATH
```

可能是：

```text
/usr/local/bin:/usr/bin:/bin
```

------

## 27.2.2 将程序参数指定为列表

`execl()` 和 `execlp()` 用列表方式传参。

例如：

```c
execlp("ls", "ls", "-l", "/tmp", NULL);
```

最后必须是 `NULL`。

容易错：

```c
execlp("ls", "ls", "-l", "/tmp"); // 错，缺 NULL
```

------

## 27.2.3 将调用者的环境传递给新程序

默认情况下，很多 exec 函数会继承当前进程环境。

例如：

```c
extern char **environ;
```

`execvp()` 会使用当前环境。

如果你想自己指定环境，用带 `e` 的版本，例如：

```c
execle("/bin/ls", "ls", NULL, envp);
```

------

## 27.2.4 fexecve()

`fexecve()` 的特点是：

```text
通过文件描述符执行程序，而不是通过路径名。
```

普通 `execve()`：

```c
execve("/bin/ls", argv, envp);
```

`fexecve()`：

```c
int fd = open("/bin/ls", O_RDONLY);
fexecve(fd, argv, envp);
```

它适合一些安全场景。

因为路径可能被替换，而文件描述符已经指向了具体打开的文件。

------

# 27.3 解释器脚本

Linux 中脚本第一行常见：

```bash
#!/bin/bash
```

或者：

```python
#!/usr/bin/python3
```

这叫：

```text
shebang
```

当你执行脚本：

```bash
./script.sh
```

内核看到第一行：

```text
#!/bin/bash
```

就会实际执行：

```bash
/bin/bash ./script.sh
```

所以脚本本身不是机器码程序，而是交给解释器执行。

------

## 27.4 文件描述符与 exec()

这是很重要的点。

`exec()` 会替换进程的程序映像，但默认不会关闭已经打开的文件描述符。

例如：

```c
int fd = open("log.txt", O_WRONLY | O_CREAT, 0644);

execlp("some_program", "some_program", NULL);
```

如果 `exec` 成功，新程序仍然可能继承 `fd`。

这有时候是有用的。

例如 shell 重定向：

```bash
ls > out.txt
```

大致过程：

```text
shell fork()
子进程打开 out.txt
子进程把 stdout 重定向到 out.txt
子进程 exec ls
ls 的 stdout 已经指向 out.txt
```

------

## close-on-exec

有时不希望新程序继承某些文件描述符。

可以设置：

```text
FD_CLOEXEC
```

含义：

```text
exec 时自动关闭这个文件描述符。
```

这样可以避免：

```text
敏感文件泄漏给新程序
socket 被意外继承
管道不能及时收到 EOF
```

------

## 27.5 信号与 exec()

`exec()` 后，信号处理方式会发生变化。

重点规则：

```text
被设置为自定义处理函数的信号，exec 后会恢复为默认处理。
被设置为 SIG_IGN 的信号，exec 后通常保持忽略。
信号屏蔽字通常会保留。
```

为什么自定义信号处理函数不能保留？

因为 exec 后，原来的代码都没了。

原来的信号处理函数地址已经没有意义。

------

## 27.6 执行 shell 命令：system()

`system()` 用来执行一条 shell 命令。

例如：

```c
system("ls -l /tmp");
```

它大致等价于执行：

```bash
/bin/sh -c "ls -l /tmp"
```

也就是说，它会调用 shell。

------

## system() 的优点

简单。

```c
system("mkdir test");
```

写起来方便。

------

## system() 的缺点

### 1. 安全风险

如果命令里拼接用户输入，非常危险。

例如：

```c
char cmd[100];
sprintf(cmd, "cat %s", filename);
system(cmd);
```

如果用户输入：

```bash
abc; rm -rf /
```

那就可能执行额外命令。

所以涉及用户输入时，不要随便用 `system()`。

### 2. 效率低

因为它要：

```text
fork()
exec shell
shell 再执行命令
```

多了一层 shell。

### 3. 返回状态解析复杂

`system()` 返回的是 shell 的终止状态，不是简单的命令退出码。

------

## 27.7 system() 的实现

`system()` 内部大致逻辑：

```c
pid_t pid = fork();

if (pid == 0) {
    execl("/bin/sh", "sh", "-c", command, NULL);
    _exit(127);
}

waitpid(pid, &status, 0);
```

所以 `system()` 本质上还是：

```text
fork + exec + wait
```

------

## 第27章重点总结

```text
1. execve() 用新程序替换当前进程映像。
2. exec 成功不返回，失败才返回 -1。
3. exec 不创建新进程，PID 不变。
4. shell 执行外部命令通常是 fork + exec + wait。
5. exec 函数名中 l/v/p/e 分别表示参数传递方式、PATH 搜索、环境变量传递。
6. exec 默认继承打开的文件描述符。
7. 可以用 FD_CLOEXEC 设置 exec 时关闭文件描述符。
8. exec 后自定义信号处理函数会重置。
9. system() 简单但有安全风险，本质是 fork + exec shell + wait。
```

------

# 第28章：详述进程创建和程序执行

第28章是前几章的深入版。

它不只是问：

```text
怎么 fork？
怎么 exec？
```

而是进一步问：

```text
fork 和 exec 对进程属性有什么影响？
创建进程速度如何？
clone() 又是什么？
```

------

## 28.1 进程记账

进程记账是系统记录进程资源使用情况的一种机制。

它可能记录：

```text
命令名
用户 ID
启动时间
运行时间
CPU 使用量
退出状态
```

用途包括：

```text
系统审计
资源统计
性能分析
安全追踪
```

你可以把它理解成：

```text
操作系统给每个进程留一份消费记录。
```

------

## 28.2 clone()

`clone()` 是 Linux 特有的重要系统调用。

它比 `fork()` 更底层、更灵活。

`fork()` 可以看成：

```text
创建一个独立子进程。
```

`clone()` 可以选择共享哪些资源。

例如：

```text
是否共享内存？
是否共享文件描述符表？
是否共享信号处理？
是否共享当前工作目录？
```

这也是 Linux 线程实现的重要基础。

------

## fork() 和 clone() 的关系

普通 `fork()` 创建出来的父子进程：

```text
内存空间独立
文件描述符表独立，但打开文件对象共享
信号处理方式复制
```

而 `clone()` 可以更细粒度控制。

例如：

```text
共享地址空间 → 更像线程
不共享地址空间 → 更像进程
```

所以 Linux 下线程本质上可以理解为：

```text
用 clone() 创建的、共享大量资源的轻量级进程。
```

------

## 28.2.1 clone() 的 flags 参数

`clone()` 的核心就是 `flags`。

常见思想：

| flag            | 大致含义                       |
| --------------- | ------------------------------ |
| `CLONE_VM`      | 共享内存地址空间               |
| `CLONE_FILES`   | 共享文件描述符表               |
| `CLONE_FS`      | 共享文件系统信息，如当前目录   |
| `CLONE_SIGHAND` | 共享信号处理设置               |
| `CLONE_THREAD`  | 放入同一个线程组               |
| `CLONE_PARENT`  | 子进程与调用者拥有同一个父进程 |

重点不一定要背完整，但要理解：

```text
clone() 的 flags 决定父子之间共享什么。
```

例如：

```text
fork()：复制很多东西，父子相对独立。
clone(CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD)：更像创建线程。
```

------

## 28.2.2 因 clone 生成的子进程而对 waitpid() 的扩展

因为 `clone()` 创建的“子任务”不一定是传统意义上的子进程，它可能像线程，也可能像进程。

所以 `waitpid()` 需要一些扩展来等待不同类型的子任务。

学习重点：

```text
普通 fork 创建的子进程，用 waitpid() 回收。
clone 创建的任务，可能需要特殊选项处理。
```

对于初学者来说，不必把所有扩展细节都背下来。

你要知道：

```text
clone 让“进程”和“线程”的边界变得更灵活，
所以等待机制也要扩展。
```

------

## 28.3 进程的创建速度

这部分主要比较：

```text
fork()
vfork()
clone()
```

早期系统中，`fork()` 复制内存很慢。

现代系统因为有：

```text
写时复制 COW
```

所以 `fork()` 通常已经比较快。

但如果程序占用内存很大，或者页表很多，`fork()` 仍然有成本。

一般理解：

```text
fork()：通用，安全，现代系统中性能不错。
vfork()：特殊优化，限制多，危险。
clone()：灵活，底层，用于线程和特殊进程创建。
```

------

## 28.4 exec() 和 fork() 对进程属性的影响

这是非常适合考试和面试的点。

你需要知道：

```text
fork 后哪些属性继承？
exec 后哪些属性保留？
exec 后哪些属性被重置？
```

------

## fork() 后通常会继承什么？

子进程会继承父进程很多属性：

```text
用户 ID、组 ID
当前工作目录
根目录
文件模式创建掩码 umask
信号屏蔽字
环境变量
打开的文件描述符
资源限制
控制终端
```

但也有不同：

```text
PID 不同
父进程 ID 不同
进程运行时间统计清零
未决信号集合清空
文件锁等部分属性不继承或规则特殊
```

最核心：

```text
fork 之后，子进程像父进程的副本，但不是完全一样。
```

------

## exec() 后通常保留什么？

`exec()` 不创建新进程，所以很多“进程身份”会保留：

```text
PID 保留
父进程 PID 保留
用户 ID、组 ID 通常保留
当前工作目录保留
根目录保留
umask 保留
打开的文件描述符默认保留
资源限制保留
环境变量根据 exec 参数决定
```

但程序本身被替换：

```text
代码段变了
数据段变了
堆变了
栈变了
全局变量没了
函数没了
```

------

## exec() 后会重置什么？

常见：

```text
自定义信号处理函数被重置为默认
内存映射通常被替换
线程只剩调用 exec 的线程
atexit 注册的处理程序消失
stdio 缓冲区等用户态库状态消失
```

重点理解：

```text
exec 后，原来程序的用户态内存基本都没了。
```

所以原来注册的函数、堆数据、全局变量都不再存在。

------

# 五章放在一起理解

这五章最重要的是一条完整链路。

以 shell 执行命令为例：

```bash
ls -l > out.txt
```

shell 大致做了这些事：

```text
1. shell 调用 fork() 创建子进程。
2. 子进程打开 out.txt。
3. 子进程把 stdout 重定向到 out.txt。
4. 子进程调用 execvp("ls", ...)。
5. 子进程的程序变成 ls。
6. ls 执行完后 exit()。
7. 内核给 shell 发送 SIGCHLD。
8. shell 调用 waitpid() 回收子进程。
```

这个例子几乎串起了五章全部重点。

------

# 最需要掌握的重点知识清单

## 第一优先级：必须理解

```text
1. fork() 一次调用，两次返回。
2. fork() 后父子进程内存独立。
3. fork() 后父子进程共享打开文件对象。
4. fork() 后父子谁先执行不确定。
5. exit() 和 _exit() 的区别。
6. fork() 会复制 stdio 缓冲区。
7. wait() / waitpid() 用来回收子进程。
8. 僵尸进程和孤儿进程区别。
9. SIGCHLD 的作用。
10. exec() 成功不返回，不改变 PID。
11. shell 执行外部命令是 fork + exec + wait。
```

------

## 第二优先级：容易考的细节

```text
1. waitpid() 的 WNOHANG。
2. status 要用 WIFEXITED、WEXITSTATUS、WIFSIGNALED 等宏解析。
3. exec 默认继承文件描述符。
4. FD_CLOEXEC 可以让文件描述符在 exec 时关闭。
5. exec 后自定义信号处理函数会重置。
6. vfork() 子进程应尽快 exec() 或 _exit()。
7. SIGCHLD 处理程序里要循环 waitpid(-1, ..., WNOHANG)。
8. clone() 可以指定共享哪些资源，是 Linux 线程实现基础。
```

# 最容易混淆的概念对比

## fork() vs exec()

| 对比           | fork()         | exec()         |
| -------------- | -------------- | -------------- |
| 是否创建新进程 | 是             | 否             |
| PID 是否变化   | 子进程有新 PID | PID 不变       |
| 程序内容       | 父子程序一样   | 当前程序被替换 |
| 成功后是否返回 | 父子都会返回   | 不返回         |
| 常见用途       | 创建子进程     | 执行新程序     |

一句话：

```text
fork 是复制进程。
exec 是替换程序。
```

------

## exit() vs _exit()

| 对比                      | exit()   | _exit()  |
| ------------------------- | -------- | -------- |
| 类型                      | C 库函数 | 系统调用 |
| 刷新 stdio                | 会       | 不会     |
| 执行 atexit               | 会       | 不会     |
| fork 后子进程 exec 失败时 | 不推荐   | 推荐     |

一句话：

```text
exit 是优雅退出，_exit 是直接退出。
```

------

## wait() vs waitpid()

| 对比         | wait()     | waitpid()    |
| ------------ | ---------- | ------------ |
| 等待对象     | 任意子进程 | 可指定子进程 |
| 是否可非阻塞 | 不方便     | 可用 WNOHANG |
| 灵活性       | 低         | 高           |

一句话：

```text
waitpid 是 wait 的增强版。
```

------

## 僵尸进程 vs 孤儿进程

| 对比             | 僵尸进程         | 孤儿进程             |
| ---------------- | ---------------- | -------------------- |
| 子进程是否还活着 | 已经死了         | 还活着               |
| 父进程是否还活着 | 还活着但没 wait  | 已经死了             |
| 处理方式         | 父进程 wait 回收 | 被 init/systemd 接管 |

一句话：

```text
僵尸是“死了没人收”，孤儿是“活着没父亲”。
```

# 一个完整代码例子：fork + exec + wait

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();

    if (pid == -1) {
        perror("fork");
        exit(1);
    }

    if (pid == 0) {
        // 子进程
        execlp("ls", "ls", "-l", NULL);

        // exec 成功不会回来
        perror("execlp");
        _exit(127);
    } else {
        // 父进程
        int status;
        waitpid(pid, &status, 0);

        if (WIFEXITED(status)) {
            printf("child exited with status %d\n", WEXITSTATUS(status));
        } else if (WIFSIGNALED(status)) {
            printf("child killed by signal %d\n", WTERMSIG(status));
        }
    }

    return 0;
}
```

这段代码里：

```text
fork() 创建子进程。
子进程 execlp() 执行 ls。
父进程 waitpid() 等子进程。
如果 exec 失败，子进程 _exit(127)。
父进程解析子进程退出状态。
```

这就是 24、25、26、27 章的核心组合。

# 用一个生活类比总记忆

你可以把父进程想成一个老板。

```text
fork()：
老板复制出一个员工，员工一开始和老板拿着一样的资料。

exec()：
员工换了一个岗位，开始执行新的任务，但员工编号没变。

exit()：
员工完成任务离开公司。

wait()：
老板确认员工离职原因、任务完成情况，并把员工档案归档。

SIGCHLD：
员工离职时，系统通知老板：“你的员工状态变了。”

僵尸进程：
员工已经离职，但老板还没处理离职手续。

孤儿进程：
老板先走了，员工还在工作，公司总部接管。
```

# 学习建议

你学这五章时，不要孤立背函数。

按照这条线记：

```text
fork 创建子进程
→ 子进程可能 exec 新程序
→ 子进程 exit 结束
→ 父进程 wait 回收
→ SIGCHLD 通知父进程
→ 如果不 wait 就有 zombie
```

只要这条线理解了，后面的 `vfork()`、`clone()`、`system()`、`FD_CLOEXEC`、信号处理、进程属性变化，其实都是围绕这条主线扩展出来的。
